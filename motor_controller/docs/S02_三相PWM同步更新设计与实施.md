# S02：三相 PWM 同步更新设计与实施

## 1. 结论与实施范围

原框架分析中的第二个问题为 **S02：三相比较值未统一缓冲提交**，属于条件性风险。原代码关闭 CH1～CH3 比较值缓冲，CPU 顺序写三相 CCR；写入与计数器比较事件相遇时，可能改变当前脉冲，或在短时间内混合新旧电压矢量。

本次已在 AT32 平台实施：

1. 启用 TMR1 CH1、CH2、CH3 比较值预装载。
2. 使用统一提交函数写三相预装载值，提交过程中短暂禁止硬件更新事件，并保存、恢复 CPU 中断屏蔽状态。
3. 正常调制不触发软件更新，不重置计数器，不改变 CH4 ADC 触发时刻。
4. 停机先关闭三相输出通道；启动前在通道关闭状态清零活动比较值和待提交值，防止恢复旧占空比。
5. 扩展真实 Board 实现的主机测试，模拟三次写入之间发生更新事件。

远程项目：`/home/psibot/workspaces/drivers/FOC_Driver_V2`。实施基线：`a75d3d6`。保留用户已有的最大占空比中文注释和 S01 修改。本次未烧录或带电运行电机。

## 2. 原理：为什么顺序写 CCR 存在风险

### 2.1 电压指令是一个整体

三相 PWM 共同实现同一个电压矢量：

\[
u_{ab}=V_{bus}(d_a-d_b),\qquad u_{bc}=V_{bus}(d_b-d_c)
\]

例如从 `(0.2, 0.4, 0.6)` 切换到 `(0.6, 0.4, 0.2)`，中间若出现 `(0.6, 0.4, 0.6)`，它既不是原来的电压指令，也不是新的电压指令。

没有缓冲时，问题不仅是几个寄存器写入之间的时间差。若 CCR 跨过当前 CNT，当前半周期可能不再遇到预期比较点，造成脉冲宽度异常。具体是否发生取决于写入时间、CNT 方向及新旧比较值，不能认为每次更新都会出错。

### 2.2 预装载将“计算完成”与“硬件生效”分开

```mermaid
flowchart LR
    A[FOC 计算三相占空比] --> B[写入三个预装载寄存器]
    B --> C[等待自然更新事件]
    C --> D[三个活动比较值统一装载]
    D --> E[按新比较值生成 PWM]
```

CPU 写入的是待提交值，输出比较逻辑继续使用旧活动值。下一次允许的自然更新事件到来，三个通道一起装载完整的新指令。

### 2.3 为什么只开缓冲、或只关中断仍不够

硬件定时器独立于 CPU 中断运行。若恰好在写完第一相之后发生更新事件，硬件仍可能装载“一相新值、两相旧值”。关闭 CPU 中断只能防止其他普通中断打断代码，不能阻止定时器硬件更新。

本次采用：

```text
保存 PRIMASK，关闭普通中断
    保存 OVFEN，将 OVFEN 置 1：禁止更新事件
        写 U 相预装载
        写 V 相预装载
        写 W 相预装载
    恢复 OVFEN
恢复调用前的中断状态
    ↓
后续自然更新事件统一装载三相
```

注意 AT32 的命名：**OVFEN=1 表示禁止更新事件**。项目自带驱动函数 `tmr_overflow_event_disable()` 同样将这个位直接设为 `new_state`，不能按名称误理解为“1=允许”。本实现直接操作项目厂商头文件定义的位域。

如果提交区间跨过更新边界，该边界不执行装载，完整新值等待后续自然更新；不会为了补偿而强制软件更新。计数器和固定 CH4 比较触发继续运行。临界区应保持短小，不能在其中增加阻塞调用、日志或外设等待。

## 3. 当前 PWM 与 ADC 的时序契约

保持中心对齐计数、`RPR=0`。自然更新事件可发生在峰值和谷底，**不是每个完整 PWM 周期只发生一次**。本次不设置 `RPR=1`，避免引入尚未验证的重复计数器初始相位。

按 S01 的统一 tick 时间轴，定时器 90 MHz：

| 时刻 | Tick | 相对本周期谷底的时间 |
|---|---:|---:|
| 谷底，开始上数 | 0 | 0 μs |
| CH4 触发 ADC 序列 | 2088 | 23.200 μs |
| 计数峰值 | 2249 | 24.989 μs |
| ADC 完整序列预算结束 | 2409 | 26.767 μs |
| 下一个谷底 | 4498 | 49.978 μs |

```text
CNT        /\                    /\
          /  \                  /  \
         /    \                /    \
时间 ----0-----峰值-------------谷底----峰值---->
               ↑                  ↑
         ADC 序列跨过峰值      正常情况下提交新 PWM
                 └─中断、FOC计算、写预装载─┘
```

正常预期：当前采样对应旧 PWM，序列结束后完成 FOC 计算，**在下一个谷底前完成三相写入并恢复更新事件**，新指令从该谷底生效。

从完整序列预算结束到谷底，约有 **23.21 μs**。这不是全部可用于算法的净时间，还须扣除中断响应、编码器读取、其他计算、提交耗时和安全余量。321 tick 是配置预算，实际延迟必须测量。

**本实现保证三相提交完整性，不保证 FOC 一定赶上谷底。** 若错过谷底，可能在后续峰值才装载；三相仍一起更新，但控制延迟增加，且完整周期内可能出现两半周期使用不同指令的情况。当前没有新增计算超时检测，不能将该风险描述为已经消除。验收时必须测量最坏执行时间；若超时，应先优化执行路径或设计明确的截止期与故障处理策略。

## 4. 停机、启动和低侧制动

开启缓冲后，“写 CCR=0”仅表示提交零值，不能单独作为立即停机保证。

本次 `pwm_hw_stop()` 先关闭三相输出通道，再提交零值，因此停机不等待下一次更新事件。这里的“立即”指软件执行关闭通道操作，不代表纳秒级同时关闭三相，也不替代驱动器硬件保护。

启动前执行：关闭通道 → 暂时关闭三相比较值缓冲 → 写零活动值 → 恢复缓冲 → 开启通道。这样即使上次非零活动值尚未被零预装载覆盖，也不会在重启时重新输出旧电压矢量。此过程不对运行中的 PWM 执行软件更新或计数器复位。

普通低侧制动零值通过统一提交函数写入，会等待自然更新；在定时器正常运行、更新允许且无后续覆盖时，边界等待不超过约半个 PWM 周期，即约 25 μs。它不是紧急关断接口。现有校准路径随后调用启动接口，启动接口会先清零活动值，因此仍从零比较值开始。校准是否使用独立新样本属于 S03，本次没有顺带修复。

## 5. 对整个控制系统的影响

| 方面 | 影响与边界 |
|---|---|
| 电流环 | 输出电压矢量按统一硬件边界生效，消除三相寄存器提交造成的新旧混用路径；新增明确的等待边界延迟 |
| 转矩与电流纹波 | 有助于减少异常脉冲导致的扰动；改善幅度需波形和电流实测，不能承诺具体百分比 |
| 控制带宽 | 延迟消耗相位裕度；应在实测总延迟后复核 PI，不宜直接沿用“CCR 写入即生效”的模型 |
| 速度／位置环 | 通过电流环间接受益；其运行频率、参数与控制结构未修改 |
| 电压利用率 | S01 的最大比较值 1908、最大占空比约 84.84% 保持不变 |
| ADC | 物理通道、序列和触发位置不变；新值在正常时序下于采样后的谷底装载，避免当前采样窗口中途改变输出指令 |
| 效率 | 不直接提升母线利用率，也不直接降低开关频率；若减少异常电流，可能减少额外损耗，需实测 |
| 保护 | 停机先关闭输出通道，不依赖缓冲装载；硬件过流保护仍独立承担保护职责 |
| CPU 开销 | 增加短临界区及更新禁止位操作；会短暂延迟普通中断，实际耗时需测量 |
| 其他平台 | STM32/GD32 实现不变；同步提交是通用要求，但寄存器语义和更新时序应由各平台独立实现 |

延迟对控制环的相位影响可用纯延迟近似理解：

\[
\Delta\phi=-360^\circ fT_d
\]

例如额外 25 μs 延迟在 1 kHz 处对应约 9° 相位滞后。这里只用于说明延迟的重要性，**不是本项目已测得增加 25 μs，也不是带宽测试结论**。实际总延迟包括采样、计算、等待装载与 PWM 保持效应。

扩展的 Board 测试模拟每次 CCR 写入后出现自然更新请求，确认临界区内活动值不出现部分新值，允许更新后一次装载完整值；验证调用前已关中断或已禁止更新时，返回后保持原状态；验证重新启动不会输出残留非零活动值。

主机测试中的定时器行为是按预装载语义建立的模型，并非实际 MCU 外设仿真，不能代替示波器验证。

### 上板验收步骤

1. 限流电源、低母线电压下，用 GPIO 标记 ADC 中断进入和三相提交完成。
2. 同时观察三相 PWM 与 ADC 触发参考，确认新占空比在预期谷底统一装载，CH4 周期和位置不变。
3. 人为使写入靠近边界，确认没有一相新值、两相旧值的提交；检查错过边界时的实际装载时刻。
4. 测量最坏 FOC 执行时间，覆盖编码器访问、通信中断和保护路径，确认含裕量后仍满足谷底截止期。
5. 非零占空比停机后立即重新启动，检查没有旧脉冲；验证故障关断不等待更新事件。
6. 核对电流波形、转矩噪声及阶跃响应，再决定是否调整 PI。不能仅凭编译通过认定闭环稳定性已经验证。
