# 同步扫频录波与频响（develop-V3.0）

扫频窗口左侧复用 Scope 显示同步给定和 Iq 原始反馈，右侧同时显示增益、
相位（主值）及相干性。滚轮缩放、拖动平移，“录波全览”恢复整个采集区间。
结果选择器可切换“设备 H1”和“完整录波复算 H1”，两者来自同一次运行。
录波缺样、乱序、非有限值或中止时，不把不完整数据补齐后计算带宽。
设备端频响仍可独立保存；没有 −3 dB 交点不等同于通信或采集失败。

## 使用

1. 使用配套固件和上位机，选择设备多正弦、逐频正弦或 Chirp。
2. 按原流程确认空载安全、CST 已使能及零给定，开始一次测试。
   仅启动扫频的协议请求开启录波；正常控制/普通遥测不上传此数据。
3. 扫频完成自动失能。等待尾帧完成，检查“完整 / 缺样 / 拒收帧”。
4. “导出频响与原始数据”保存 name.csv（设备频响）、name.csv.samples.csv
   （元数据和 binary32 可往返的十进制原始样本）以及 name.csv.txt（诊断）。
   在“导入扫频采样 CSV”选择 .samples.csv 可离线重新显示和复算。
   主机低频兼容模式的旧 CSV 格式保持支持。

当前设备/录波复算的 H1 使用相同整周期窗口：多正弦 50 ms 稳定 + 3×50 ms；
Chirp 1 s 稳定 + 3×1 s；逐频法每点先稳定，再取 4 个各 4 周期的块。
复算使用真实上传的输入频谱，double 累加，不使用主机合成激励代替实际给定。
不把闭环相位直接解释成开环相位裕度。

## 固件和协议

- FOC_SWEEP_ENABLED=0 移除扫频/录波 RAM 和运行路径。
- 0xBC 原有 11 字节控制字段不变；可选 [11]=0xA9,[12]=1 开启本次录波。
  CAN-FD 补零不能误开启。旧主机继续只取设备频响。
- 成功/普通 0xBC/0xBD 应答在原 40 字节后附 [40]=0xA9,[41]=1,[42]=enabled。
  原拒绝/运动诊断扩展优先保留；新主机兼容旧固件无录波的应答。
- 0xBF 为设备主动上传，payload（不含 CNT/CMD）：

| 偏移 | 字段 |
|---|---|
| 0 | 版本 1 |
| 1 | 样本对数 1–6 |
| 2–3 | 运行编号，uint16 大端 |
| 4–7 | 本包第一个设备采样序号，uint32 大端、从 0 开始 |
| 8… | 连续的 input / feedback，各 IEEE-754 binary32 大端，单位 A |

一帧最多 6 对样本，保留 20 kHz 原始采样，既不抽取也不缩放为整数。
采样序号和状态帧的总样本数共同发现开头、中间及尾部缺失。
运行编号隔离迟到数据；旧运行帧不会混入新的采集。
x[n] 是本周期施加的给定，y[n] 在施加前采样，真实控制延迟保留。

sweep_record 是独立单生产者/单消费者模块，静态 RAM 232 B，四个六样本槽。
20 kHz 下能缓存约 1.2 ms 数据。中断只复制数值/发布槽，不发送 CAN、
不申请内存、无循环和频谱计算；原有控制耗时监测包含新增采样开销。
前台复用 CAN-FD 发送函数，普通控制应答优先，发送忙时保留槽重试。
缓冲满时丢新样本但不修改设备 H1；上位机明确报告序号缺口，不伪装成完整录波。
这不是断线后可补传的整段录波存储，持续总线拥塞仍可能造成缺样。

## 2026-11-24：Chirp 实机超时/录波缺样后的优化

截图显示在第 20712 个采样周期中止（1.0356 s），FOC 峰值 46 μs 超过
现有 45 μs 测量预算；录波只收到 14028 点，缺失 6684 点。此时尚未完成
第一个 1 s 估计块，因此没有可发布的频响。缺样与耗时超限是两个独立问题。

- Chirp 将稳定/测量/块末分支移到频点循环外；稳定期不再更新无人使用的
  DFT 相位，进入测量时仍复位到相同相位。浮点运算顺序和频谱归一化不变。
- 录波槽直接保存现有 v1 线格式；ISR 对浮点位模式做 REV/存储，不做数值
  转换。前台发送忙时重试原槽，避免反复构造 56 字节负载和额外栈缓冲。
- 传输层提供可选 tx_ready 提示，协议在复制数据前返回忙；send 自身仍检查
  硬件状态。录波期间普通高频遥测限到 20 Hz，并暂停竞争的 debug 流；
  原来更低的遥测频率或关闭设置保持有效，控制应答仍优先。结束自动恢复。
- 中止后自动全览已有录波；Scope 的全览操作使绘图缓存失效，避免沿用旧时间轴。

20 kHz、每帧 6 对样本仍需要约 3333 帧/秒；保留 binary32 和真实采样序号，
不抽样、不平滑补洞、不改 45 μs 保护阈值。缓存仍只有 24 对样本（约 1.2 ms）。
这些改动减少软件开销，不能保证在持续总线拥塞或前台长时间阻塞时无丢样。

ARM 构建：APP 53504 B / 55296 B，余量 1792 B；静态 RAM 14080 B，
主数据区余量仍为 344 B。与上一录波版相比 Flash +176 B、RAM +0 B。
离线验证包括 27 组配置、1431600 个样本的新旧 C 引擎逐位一致性，
三种模式真实 C 采集帧到 C++ H1 复算、TX 忙/应答优先/遥测恢复及中止界面。
尚未进行这版固件的实机复测，不能把静态代码优化当作实测耗时下降。


## 2026-11-24：持续录波缺样，发送流水线修复

最新有效的 run 16935：前 1 s 收到 20000/20000 点，后 3 s 分别收到
14098、14041、14057 点，总计 62196/80000，缺失 17804 点。
设备完成且 flags=0；缺样不等于 FOC 中止。多数缺口不是 6 点整数倍，
与设备小缓冲溢出相符；不能仅靠增加主机普通遥测频率解决。

调度改动：

- AT32M416 的高优先级 PTB 保留给普通应答、状态和 IAP；录波 0xBF 通过
  三深度 STB FIFO，利用控制器自身缓冲，让前台装帧与 CAN 总线发送重叠。
  原来的单 PTB 路径必须等待当前帧发完，才能装下一帧。
- `comm_frame_t.bulk` 使用结构原有填充，传输层不依赖扫频命令号。
  自定义协议负责把录波标记为 bulk，所有 RX 帧显式初始化为 false。
- STB 写入成功即移交所有权，不因为已有 TSALL 发送或 TSNEXT 尚未提交完成
  而重传同一帧。每轮前台重新检查待发送 FIFO，覆盖末帧延迟提交和清空边界。
- 每轮最多提交三帧，FIFO 忙立即返回；不增加关中断区、不在 ISR 发送、不忙等。
  有排队应答时仍先处理应答，返回主循环继续运行保护和收命令。
- 频谱累积继续在采样 ISR，H1 结果归约仍在前台；不把浮点累积搬到不均匀
  调度的上传路径。保留上一版 Chirp 阶段判断外提，所有频点/窗口/累积顺序不变。
- 原始 20 kHz、binary32 输入/反馈、采样序号及物理一拍延迟不变。
  不抽样、不插值补洞；缺样录波仍禁止用于带宽复算。保护阈值保持不变。

诊断扩展（兼容旧 A9/1）：状态负载 byte 43=0xAA，44..47 为设备缓冲丢样
uint32 BE，48..51 为已移交 CAN 样本数 uint32 BE，总长 52 B。
旧零填充帧没有 AA 标记，不会被误识别。拒绝 A7、运动中止 A8 保持原格式。
计数是最后一次状态读取快照，CAN 提交不代表主机收妥；仍以主机最终样本序号
检查完整性。两个计数在新录波开始清零，设备丢样计数只在确实丢样时递增。
上位机同时显示并随诊断文本/录波元数据导出该快照。

资源：APP 53872 / 55296 B，剩余 1424 B；静态 RAM 14088 B，主区余量
336 B。录波模块 240 B，比上一版增加 8 B 计数，未扩大软件样本缓冲。
EFW 容器 53904 B（含 32 B 文件头，头不烧入 APP）。关闭扫频宏构建也通过。

验证：真实传输函数的 FIFO 满/延迟提交/清空边界/优先级/忙重试测试通过；
模拟前台每 200 us 获得发送机会、每帧服务 220 us 时，新路径完整传输
80000 点并允许控制应答插入；人为阻塞 2 ms 时仍如实报告 21 点丢失。
这些是确定性调度模型参数，不是实测 MCU 耗时或实际总线帧长。
三种波形及 H1 数值回归、时序/运动/电流/电压保护、默认关闭、CAN RX FIFO、
命令 ACK 和 54 KiB 升级边界测试通过。10 组上位机测试通过，新诊断和旧固件
兼容 UI 再次通过。FOC/PID/编码器/扫频引擎/Chirp/准备/保护适配器的 ARM
函数段逐字节保持一致。尚未烧录或进行本版实机验证。

复测保持普通设备遥测 1000 Hz；扫频期间已有 20 Hz 状态限流。
CAN-FD 保持仲裁段 1 Mbps / 数据段 5 Mbps。先用相同参数复测，核对
80000/80000、设备丢样 0、flags=0 和 FOC 峰值；失败时保存三个导出文件及日志，
不要通过放宽保护阈值或增加普通遥测频率掩盖缺样。


## 2026-11-24：FIFO 版本实机仍缺样后的热路径优化

FIFO 版实机仍有持续缺样：run 27570 完成 80000 点，设备丢弃 15089 点、
提交 CAN 64911 点且主机全部收到。稳定阶段 20000/20000，估计阶段分别
14968、14950、14993 点；首个缺口在 1.0026 s。随后固定 PID 的截图仍缺
15149 点。FIFO 并未解决持续吞吐不足，之前的调度模型不能代表实机 CPU 预算。

本次生产代码只修改 CAN 端口和 Chirp 热循环：

- CAN 标准数据帧直接写控制器缓冲，删除临时 can_txbuf_type 清零、完整负载
  中转复制以及逐字节移位重组。控制字 TBSEL/TSNEXT 保持厂商驱动原字节写序列；
  数据经 memcpy 取 uint32，避免未对齐指针/严格别名转换。部分字和 DLC 尾部
  显式补零，不越界读取。保留 PTB 应答优先和 STB 有界提交/重试规则。
- DLC 换算与原表完全一致，改为固定分支，64 B 热路径不再线性遍历 16 个表项。
- Chirp 估计循环缓存本频点原相位并按指针遍历，减少地址乘法、重复读取与
  存储后重载；每个振荡器及累加器的浮点算式、相位时序和块边界不变。
- ARM 实际 32 位负载复制循环为 LDR、STR、SUBS、BCS 四条指令/字；发送函数
  自身栈帧由 96 B 降为 40 B（不含被调用函数/中断叠加，不能等同总栈峰值）。
  指令减少是静态证据，不换算为未经实测的微秒或零丢样保证。

未修改 20 kHz 采样、binary32 数据、H1 窗口/归一化、相干性门限、保护阈值、
PID 或中断优先级，也没有通过增加队列 RAM 掩盖持续堵塞。

验证包含 27 配置、1431600 样本的真实 C 引擎逐位比较（激励和所有频点统计），
冻结参考引擎及测试已纳入 tests/run_sweep_tests.py。直接 CAN 写入与实际厂商
can_txbuf_write 比较 1560 组：PTB/STB、长度 0..64、4 种源地址对齐及 3 个 ID；
另以独立 DLC 表检查长度编码。满队列、提交延迟、重试和尾帧测试保留。
原 FOC/PID/编码器/Chirp 波形/准备/保护适配器 ARM 函数段与上一版保持一致。
9 组固件本机套件及 10 组上位机 CTest 通过，扫频启用和关闭 ARM 构建均通过。

APP 53704 / 55296 B，余量 1592 B，比 FIFO 版减少 168 B；静态 RAM 14088 B，
主数据区余量 336 B，RAM 增量 0。EFW 共 53736 B，包括不写入 APP 的 32 B 文件头。
固件/上位机已重新构建，尚未烧录或实测本版吞吐；仍需以完整 80000 点、设备
丢样 0、flags=0 和原始日志验证。升级后先读回并恢复原来的 Kp/Ki，避免混入
默认参数的频响差异。即使录波完整，Chirp 相干性不足的频点仍不能用于带宽交点。
