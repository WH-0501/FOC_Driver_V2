# CAN 命令落后一帧：下位机接收修复

## 问题及修改

当前固件 `CAN1_RX_IRQHandler()` 调用传输层后才清 RIF，传输层每次只调用一次 `can_rxbuf_read()`。RIF 是事件标志，不是待收帧计数；两帧在中断前进入 FIFO 时，读取一帧后清标志，会把另一帧留到下次接收事件。后续单次查询始终只能推动上一条命令。

离线测试直接编译项目中的实际 IRQ 和 RX 队列函数，已在原代码复现“两帧进入→只处理一帧→下一帧来时才处理前一帧”。此缺陷与真机 CNT/ACK 连续落后一条的日志吻合；是否为运行中设备的全部原因仍以更新后验证为准。

修改两处：

1. 接收中断先清本次观察到的标志，再调用传输层；避免收帧过程中出现的新事件被随后清掉。
2. 传输层循环读取硬件 FIFO，每次 IRQ 最多处理 6 帧。若仍有待收帧，软件挂起 CAN RX IRQ 继续处理，不需要主机多发一条命令。软件环形队列满时仍释放硬件帧并计数，不阻塞硬件 FIFO。

参考：[AT32M412/416 官方数据手册](https://www.arterychip.com/download/DS/DS_AT32M412_416_V2.01_EN.pdf)描述了六级接收 FIFO；本次修改不改波特率、控制模式、PID、使能协议或 CAN 盒兼容代码。

## 验证

- 原实现：离线成功复现永久残留一帧。
- 修复实现：双帧、单帧、空中断、FIFO 满、软件队列满、IRQ 预算耗尽续收、处理中新增 RIF、环形队列回绕通过。
- 原有 command ACK 回归通过。
- Keil ARM Compiler 5.06u7 完整重编译：0 错误、6 警告，详见 `firmware-build.log`。
- 额外运行原仓库 PID 编码测试，既有 `test_cur_pid_ki_scale` 断言失败；该失败发生在未修改的原测试与原 GUI 编码代码中。本次没有修改 PID 或旧 GUI，不能声称全部原仓库测试通过。
- 本次未向真机发送任何 CAN 帧，未烧写、复位或使能真实设备。

## 交付与更新

`motor_controller.hex` 是应用程序映像，起始地址为 `0x08001000`；`motor_controller.bin` 为对应原始应用；`AX58400_AT32M416_APP.efw` 是项目原 FileInfoAdder 生成的 ASIX 类型 3 包。校验和、HEX 地址范围及二进制向量在 `manifest.json` 中记录。

原 `motor_controller_gui` 保持不变。原工程的已有 `main.c` 修改保留，原 `objects`/`FoE` 产物未覆盖；固件在隔离副本内重编译。补丁为 `can-rx-fifo.patch`，源码修改也已应用至当前工程。

这不是只更新 MotorTune.exe 就能生效的改动。设备仍运行旧固件，需通过现有受控烧录流程更新应用。日志中最后的 `02 40 01` 可能仍在接收队列，继续发查询可能触发此前的使能；应先确保设备处于可安全复位/断电的状态。此包尚未在真机烧录验证，不能把构建通过当成设备已修好。

更新后的验收：先以设备失能状态验证单条 B5 的 ACK CNT 与本次请求一致，等待数秒无需追加任何查询；随后在确认工作区安全后测试单次使能/失能。仍保持连接一次 B5、后续人工查询，不能恢复轮询掩盖延迟。
