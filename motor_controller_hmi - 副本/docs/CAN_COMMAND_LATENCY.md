# 单次命令延迟调查与收发修订

## 已确认的证据

用户日志（2026-11-04）：

| 下发 | 此时收到的 ACK |
|---|---|
| 10:45:59 `00 B5` | 无，2 秒后超时 |
| 10:46:07 `01 B5` | `00 B5`，前一次读取 |
| 10:46:14 `02 41 01` | `01 B5`，前一次读取 |
| 10:46:24 `03 40 01` | `02 41`，前一次模式命令 |

这是应答连续落后一条请求的证据，不是“C++ 运算性能不足”的证据。仅凭主机日志，尚不能确定滞留在 USB/CAN 发送、设备接收处理还是应答回传。

逐项核对旧版：`motor_controller_gui/core/motor_client.py` 使用相同的 CNT/CMD/payload 和 CAN FD 长度填充；`canbus/zlg_native.py` 使用相同的标准 ID、BRS=1、normal transmit、1M/5M ISO 参数；两套程序部署的 ControlCANFD.dll SHA256 一致。

旧版 `ui/speed_limit_widget.py` 的可见限速区每 500 ms 发送 B5。推断：持续查询可能使“必须有下一帧才处理前一帧”的问题表现为最多约 500 ms 的延迟，不能用旧界面看起来成功排除底层积压。没有通过新增轮询、重复使能或延长超时掩盖此现象。

## 本次变更

- 普通进度、连接成功、使能/失能成功不展开全局提示条。进度由按钮显示，成功体现在设备状态；失败和异常保留常驻提示。
- 原生接收独立线程，沿用旧版发送/接收并行调用方式。发送不再等待接收 DLL 调用结束。接收队列有 65536 帧上限，退出时先结束接收再关闭驱动，不并发卸载 DLL。
- 增加 TX 驱动提交时间、主机排队时间和匹配计数器的 ACK 往返时间日志。超时后保留最近 30 秒、最多 256 条事务以识别迟到 ACK。
- 同命令超时后重新手动请求时，未经匹配 ACK 的专用结果先暂存；属于旧请求的结果不完成新请求。没有歧义的旧协议专用应答路径保留。
- 失能/使能仍需新遥测确认，ACK 或发送函数返回成功不能单独代表设备已执行。
- B5 仍然仅连接成功读一次、后续手动点击查询；B6 仅点击发送。没有自动命令重试或额外“冲刷”帧。

## 验证与边界

新增测试专用 DLL（仅位于 build 的 test-driver，不随产品部署）：核验 64 位句柄、初始化布局、76 字节发送结构、80 字节接收结构、帧内容和大时间戳；人为阻塞 ReceiveFD，验证 TransmitFD 仍可独立执行，并确认空闲时无额外发送。

事务测试复现 B5 首次超时、第二次先收到前一条应答和旧 ACK，随后收到自身应答，验证不会把旧值作为新回读成功。窗口测试检查正常操作不展开提示条。

## 只读真机对照结果

发现 CAN1 有 Node 1 周期遥测后，分别打开/关闭原生后端及旧版 Python ctypes 后端，每次只发送一条 B5，观察 2.5 秒，不发送使能、失能、运动、轮询或冲刷帧。

| 路径 | 本次请求 | 驱动提交耗时 | 观察到的 ACK |
|---|---|---|---|
| 修改后的 C++ 原生 | `00 B5` | 0.0924 ms | `70 B5`（旧请求，约 13 ms 到达） |
| 旧版 Python ctypes | `A5 B5` | 0.0892 ms，返回 1 | `00 B5`（上次 C++ 请求，约 0.56 ms 到达） |

两个观察窗口分别收到 3957、3962 帧周期遥测。说明主机并没有整体停止接收；改为并行收发后，“应答落后一条”仍可复现，旧版 Python 单次发送也一样。旧版持续 B5 查询掩盖此现象的解释得到进一步支持。原始结果保存在同目录的 `native-single-query.json`、`legacy-single-query.json`。

尚不能仅凭这两份主机日志把滞留位置确定为 CAN 盒/USB 驱动或下位机。需要总线侧抓包或者设备接收队列观测进一步区分。未修改/烧写固件；不把 8 组自动测试通过或本次并行收发改动写成真机使能问题已解决。
